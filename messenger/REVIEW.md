# LEXI Messenger: разбор клиента и сервера

Для Георгия. Что было в `client.js`, `server.py` и `crypto_utils.py`, что исправлено на стороне клиента и что осталось сделать на сервере.

Коротко: E2E-шифрование работает уже сейчас, через твой `server.py` без единой правки. Это проверено двумя клиентами: сервер ретранслирует сообщения, а в его лог попадает только шифротекст. Транспортный ML-KEM на сервере пока заглушка. Клиент это видит и показывает янтарным статусом «заглушка KEM». Ниже список того, что нужно, чтобы статус стал зелёным.

---

## 1. Клиент (`client.js` → `js/lexi-client.js` + `js/lexi-e2e.js`)

| # | Было | Чем грозило | Стало |
|---|------|-------------|-------|
| 1 | `encryptMessage = btoa(message + key)` | Шифрования нет совсем. Ключ дописан к тексту и лежит прямо в «шифротексте». На кириллице `btoa` падает с исключением | AES-256-GCM через WebCrypto, IV 96 бит, AAD = `LEXI1‖канал‖эпоха‖автор‖id` |
| 2 | Ключи из `Math.random()` в hex | Генератор предсказуем, и ключи не являются ключами ML-KEM | Настоящий ML-KEM-768 (FIPS 203) из `noble-post-quantum`, тот же бандл, что в LEXI Space. Случайность берётся только из `crypto.getRandomValues` |
| 3 | `sharedKey = generateRandomHex(32)` после рукопожатия | У клиента и сервера получаются разные ключи, поэтому зашифрованные сообщения не расшифровываются никогда | Клиент делает `encapsulate` под ключ сервера и шлёт `ciphertext`. HKDF с теми же солью и info, что в `crypto_utils.generate_symmetric_key`. Совместимость проверена: шифротекст из JS расшифровывается твоей `decrypt_message` |
| 4 | Тип `encrypted_message` | Сервер такой тип молча игнорирует | E2E-конверт `LEXI1.msg.{…}` едет в обычном `content` типа `message` |
| 5 | Рассылка сервера приходит без `type` | Клиент кладёт её в `unknown_message`, и чат пустой | Кадр с `content` и `channel` распознаётся как `message` |
| 6 | Переподключение: `this.connect(...).then(resolve)` внутри `onclose` | Цепочка из уже выполненных промисов. Срабатывает и после ручного `disconnect()` | Отдельный `_scheduleReconnect`: экспоненциальная задержка с джиттером, до 6 попыток. После `disconnect()` переподключения нет |
| 7 | Два обработчика `'error'`, `console.log` с содержимым сообщений | В консоль и логи попадает открытый текст | Журнал без содержимого, события через `on/off` |
| 8 | `setTopic(channel, topic)` шлёт 2 аргумента | Сервер принимает только 1, тема не ставится | Тема шифруется как сообщение канала. Опционально её можно продублировать командой `TOPIC [topic]` |

Публичные методы и их имена сохранены (`connect`, `joinChannel`, `sendEncryptedMessage`, `sendCommand`, `listChannels`, `listUsers`, `setTopic`, `disconnect`, `on/emit`), поэтому код, написанный под старый клиент, не сломается.

### Как устроено E2E поверх текущего сервера

```
участник A                         server.py (ретранслятор)          участник B
  │ LEXI1.pk  {uid, pk ML-KEM 1184 Б}  ──────────────►  всем в канале
  │                                                     │ LEXI1.pk (ответ)
  │ encapsulate(pk_B) → ct 1088 Б, ss
  │ K_wrap = HKDF(ss, "LEXI-E2E-v1", канал|эпоха|B)
  │ LEXI1.key {to:B, kem_ct, iv, AES-GCM(K_wrap, K_канала)} ──►  decapsulate → K_канала
  │ LEXI1.msg {epoch, id, iv, ct}  ◄────────────────────────────►  AES-256-GCM
```

* Ключ канала (32 байта) создаёт первый участник, это «основатель эпохи». Эпоха = время создания + случайный хвост. Если два основателя появились одновременно, все сходятся на самой ранней эпохе.
* Новичок объявляет свой открытый ключ, и кто-то из держателей ключа (со случайной задержкой, без дублей) заворачивает ему ключ канала.
* Сообщения неизвестной эпохи ждут в очереди, а клиент запрашивает нужный ключ (`need`).
* Подмену ключа сервером закрывает сверка отпечатков (SHA-256 открытого ключа) в «Инфо о чате».

## 2. Сервер (`server.py`): что поправить

Блокеры, по порядку важности:

1. **Взаимная блокировка в `broadcast_message`.** Функция держит `data_lock`, а при ошибке отправки вызывает `disconnect_client`, который снова берёт тот же `asyncio.Lock`. Lock нереентерабельный, поэтому один «мёртвый» сокет навсегда вешает все рассылки сервера. Нужно собирать список отключившихся под замком, а отключать их после выхода из него.
2. **Транспортный KEM — заглушка.** `server_public_key = os.urandom(32)`, а `shared_key = os.urandom(32)` никак не связан с клиентом. Исправление (пакет `kyber-py`, чистый Python, ставится и на Windows: `pip install kyber-py`):
   ```python
   from kyber_py.ml_kem import ML_KEM_768
   from crypto_utils import generate_symmetric_key   # соль/info уже совпадают с клиентом

   ek, dk = ML_KEM_768.keygen()                      # 1184 / 2400 байт
   await websocket.send_text(json.dumps({"type": "pqc_handshake",
       "server_public_key": base64.b64encode(ek).decode(), "user_id": user_id,
       "frames": "aes-256-gcm"}))                     # клиент начнёт шифровать кадры
   resp = json.loads(await websocket.receive_text())
   ss = ML_KEM_768.decaps(dk, base64.b64decode(resp["ciphertext"]))
   user.shared_key = generate_symmetric_key(ss)
   # дальше кадры {"type":"sealed","data":...} → crypto_utils.decrypt_message(data, key),
   # ответы — {"type":"sealed","data": crypto_utils.encrypt_message(json, key)}
   ```
   Проверено: браузер инкапсулирует секрет (noble), `kyber-py` его восстанавливает, и `crypto_utils.decrypt_message` расшифровывает кадр. Формат `sealed` тот же, что у `encrypt_message`/`decrypt_message`. Демо-ретранслятор (`js/demo-relay.js`) уже работает по этому протоколу, по нему можно сверяться.
3. **Логирование открытого текста:** `logger.info(f"...: {content}")`. С E2E туда попадает шифротекст, но для старых клиентов строку нужно убрать совсем.
4. **`disconnect_client` чистит только «домашний» канал.** Из каналов, куда клиент вошёл командой `JOIN`, сокет не удаляется, и рассылка продолжает в него писать (а это ведёт к пункту 1).
5. **`quit_channel` удаляет ключи словаря во время итерации** (`del users_in_channels[channel]` внутри `for`). Это `RuntimeError`.
6. `if ws != sender_id` в рассылке сравнивает сокет со строкой, поэтому фильтр ничего не делает. Клиенту так даже удобнее: эхо служит подтверждением доставки и мерой RTT. Если отправителя исключать, нужно присылать ему `{"type":"ack","id":…}`.
7. В `Message.to_dict()` нет поля `"type": "message"` и имени отправителя. Клиент это обходит, но лучше добавить.
8. Нет `PART`: выйти из одного канала нельзя, только `QUIT` из всех.
9. Нет истории. Предлагаемый кадр после `join_success`: `{"type":"history","channel":…,"messages":[{…как message…}]}`. Хранить только `LEXI1.msg`-конверты, по схеме из `sql/schema.sql`.
10. Нет ограничения размера кадра и частоты. Нужны `ws_max_size` у uvicorn и лимит сообщений в секунду на сокет.
11. Нет аутентификации: имя берётся из `init` как есть. Таблицы `users`/`sessions` и функции `auth_lookup`/`auth_result` в схеме готовы под вход с Argon2id.

## 3. `crypto_utils.py`

* `encrypt_message`/`decrypt_message` и HKDF корректны, клиент совместим с ними байт в байт.
* `generate_keypair`, `encapsulate`, `generate_shared_secret` — это симуляция (`os.urandom` и `sha256(private‖public)`). Их надо заменить на ML-KEM из `kyber-py` или `liboqs-python` (см. пример выше).
* Постоянная соль HKDF допустима (RFC 5869), но в `info` полезно добавить `user_id` и id сессии, чтобы ключи разных сессий были разведены даже при повторе секрета.

## 4. Что ещё не сделано (честно)

* Ключи личности живут одну сессию. После перезагрузки вкладки ключ новый, и отпечатки нужно сверять заново. Следующий шаг — долговременный ключ ML-DSA-65, который подписывает сеансовые ключи ML-KEM (поля в `identity_keys` уже есть).
* Ротации эпохи при выходе участника пока нет: старый участник с ключом может читать дальше, если сервер продолжит слать ему кадры. В схеме для этого есть `channel_epochs.retired_at`.
* Премодерация, «Зал славы», голосования и метки ИИ работают на клиентах, потому что сервер содержимого не видит. Модератор — тот, кого основатель канала указал в зашифрованном `config`.
